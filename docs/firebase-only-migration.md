# Firebase-only migration

The public site keeps its existing addresses. Publishing, drafts and revision history stay available, and People and Journal remains invitation-only. Hosting has a 1 GB project-wide cap. Website artwork moves to the existing Firebase Storage bucket. Originals, ZIPs and recovery artifacts stay in `archives/` on the local machine.

## Backend decision

The approved path uses a second-generation Firebase HTTP Function for the existing Astro server. Production deployment uses the existing Blaze project and enables Cloud Build and Artifact Registry as deployment dependencies. Firebase manages the Cloud Run service underneath. The function scales to zero and uses bounded instances. These settings limit usage but do not cap billing. [Firebase Functions infrastructure](https://firebase.google.com/docs/functions/version-comparison) · [Deployment and billing requirements](https://firebase.google.com/docs/functions/faq-and-troubleshooting)

The Firebase Function reuses the existing invitation checks, admin authentication, publication transactions, scoped API and media authorization. Hosting sends pages and API requests to the pinned function. The release stage puts fingerprinted public artwork and precomputed WebP variants in the existing Storage bucket. Existing public image paths redirect to that isolated prefix. CMS uploads and People and Journal media still go through the authenticated application endpoint.

## Sequence

1. Establish a cost baseline. Verify active versus soft-deleted Storage bytes, billable download regions and recent requests. Keep live and draft media referenced by entries, revisions or publications. Never infer that an object is unused from its age or publication flag alone.
2. Stage only public webpage art from the local build. Generate responsive, fingerprinted renditions. Reuse the existing `us-east1` bucket in a dedicated public-art prefix. Permit object reads only for that prefix and verify that listing, writes, and anonymous access to `journal/**` remain denied. Use direct Firebase Storage URLs in pages and social metadata. Test old image links, dark mode, gallery enlargement and responsive variants. Measure the expected download and operation cost before uploading. [Firebase Storage locations and free tier](https://firebase.google.com/docs/storage/locations)
3. Build a static Hosting preview with images excluded and existing canonical URLs preserved. Keep only the HTML, scripts, fonts, styles and configuration needed to render pages. Reject a release whose proposed Hosting files plus any retained versions would exceed 1 GB. Inspect the upload manifest for raster images, SVG artwork and archives before publishing.
4. Run the existing reader, CMS and emulator checks, then deploy the preview function with the preview data namespace. Verify the Functions framework preserves JSON and multipart request bodies. Test anonymous denial, protected media, existing API routes, draft isolation and a synthetic publish without touching live content. Check the Hosting rewrite pin and the audit delivery endpoint.
5. Cut over only after the new implementation passes these checks with representative data. Keep a local recovery bundle and rehearse restoring it. Switch Hosting after both public and private journeys pass. Retire the old runtime, job schedules and registry references after the new site is healthy.

The Firebase Storage allowance is usage-based. Moving image requests from Hosting changes which product records their transfer. Keep the existing origin in place while testing the Storage path and its billing impact. [Firebase pricing](https://firebase.google.com/pricing)

## Stage and release

Run `node scripts/stage-firebase-release.mjs preview <full-git-sha>` from a clean source tree using Node.js 24. The ignored release directory contains `functions/`, the image-free `hosting/` directory, fingerprinted `storage/` objects and Firebase configuration. Review the size and paths before deployment. Use Firebase CLI 15.35.0, which supports the Node.js 24 Functions runtime. Apply the narrow public Storage rule and upload only the staged public-art objects. Deploy `journalPreview` before publishing the preview Hosting version. Stage `live` from the same reviewed revision, deploy `journalLive`, and publish its pinned Hosting config. Enable the one-day Functions artifact cleanup policy. Delete verified obsolete build inputs from staging storage once deployment has finished, and keep the Hosting release and rollback bundle local.

Use the stage's `firebase.json` with `deploy --only functions`. Verify the resulting Function's managed service and ready revision before publishing Hosting. Use the stage's `firebase.hosting.json` with `hosting:channel:deploy review --expires 1d` for preview and `deploy --only hosting` for production. The Hosting-only configuration pins the Function's existing managed revision and avoids triggering a second build. Confirm the published Hosting version, target revision and version size, then remove the temporary preview channel.
